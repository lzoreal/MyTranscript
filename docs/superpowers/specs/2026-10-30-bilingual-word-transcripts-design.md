# 中英双语词级 transcript 设计（方案 1+3）

日期：2026-10-30 状态：待评审
前序：`2026-10-28-hwmym-word-timestamps-backfill-design.md`、`2026-10-29-scraped-shows-word-timestamps-design.md`

## 目标

终极产物从"VTT + 词时间旁挂"改为**每集一份中英双语词级 JSON**；VTT 降级为中间产物，可以丢弃。
英文词时间来自 ASR；中文词时间由"小句对齐 + 句内按字分配"派生。

## 一、实测依据（2026-10-29，同一集）

| 观察 | 数据 |
| --- | --- |
| 译文小句数与原文相等 | **只有 13%**（33% 差 1、23% 差 2、18% 差 3、13% 差 4–17，且多数是中文更少） |
| 纯词级 DTW | 12% 的中文词与上一个词共用同一瞬间；出现"研究←in、抱怨←the"这类语义错配 |
| 小句级 DTW + 共享区间按字数切分 | 共用瞬间 **0%**、时间重叠 **0**、未对齐小句 **0**；中位词时长 0.23s（中文词密度导致，属正常） |

结论：**必须让翻译本身产出可校验的结构**（小句级对齐），事后对齐只作兜底。

## 二、翻译契约（结构化输出）

每句翻译要求返回：

```json
{"index": 12, "clauses": [
  {"en": "But psychologists who study complaining say", "zh": "但是研究抱怨的心理学家说"},
  {"en": "there's a right way and a wrong way to complain,", "zh": "抱怨有正确的方法和错误的方法，"}]}
```

批处理仍是"一次 50 条、按 index 回收"，只是每条的值从字符串变成 clauses 数组。

### 2.1 校验（机械、逐条）

一句翻译**通过**当且仅当：

1. `clauses` 非空；每个 clause 的 `en`、`zh` 都非空；
2. 所有 `en` 拼接后，与原句**归一化逐词相等**（小写、去标点后比较）——这一条同时挡住漏译、增译与调序；
3. 每个 `en` 的结尾落在原句的**词边界**上（即按顺序消费原句 token）；
4. 每个 `zh` 不以标点开头。

失败处理：**只重发这一句**，最多重试 2 次（第 2 次附带更严格的措辞）；仍失败 → 降级为单 clause（`en` = 整句、`zh` = 该句译文），并标记 `coarse: true`。

### 2.2 缓存兼容

`translations.json` 的条目从 `"译文"` 升级为 `{"zh": "...", "clauses": [...], "coarse": false}`；
读取时兼容旧字符串形式（视为 `coarse: true`、无 clauses）。缓存键不变（仍是 cue 文本的哈希）。

## 三、中文词时间的对齐算法

输入：一句的英文词（含真实时间）+ 该句的 clauses。

1. **小句时间**：每句的时间跨度已知（首词起点 → 末词终点）。按 clauses 的 `en` 词数比例把该跨度切给小句；
   若某小句 `en` 词数为 0（异常）则整句降级为 `coarse`。
2. **小句内**：中文分词（spaCy `zh_core_web_sm`），按字符占比把该小句的时间分给各词；标点不参与分配。
3. **单调兜底**：逐词 `start` 不小于前一词 `start`；`end > start`。

> 该算法只在**同一句内部**作业，误差不会跨句。

## 四、兜底（方案 3，用于旧数据与校验失败）

当一句没有 clauses（旧缓存、或降级后）：

1. 英文小句（按标点切）与中文小句（按中文标点切）各取嵌入（MiniLM 多语），做**单调 DTW**；
2. 一个英文小句被多个中文小句共享时，把它的时间跨度**按中文小句字数切分**（已实测：不做这一步会出现时间重叠）；
3. 中文小句内部再按字分配。

**置信度门槛**（任一触发 → 该句 `zh_words` 置空，只保留句子级中文）：

- 该句 |中文小句数 − 英文小句数| ≥ 3；
- 某小句被分配的时长 / 其字数占比，偏离该句中位数 50% 以上。

日志按集统计 `低置信句数 / 总句数`，超过 20% 在集级日志点名。

## 五、产物格式（JSON v2）

```json
{"version": 2, "episode": "<vtt stem>", "audio_seconds": 1479.11, "complete": true, "attempts": 1,
 "sentences": [
   {"start": 14910, "end": 16690,
    "en": "spouse's most annoying habit,",
    "zh": "伴侣最烦人的习惯。",
    "coarse": false,
    "words":    [["spouse's", 14910, 520], ["most", 15430, 320]],
    "zh_words": [["伴侣", 14910, 520], ["最", 15430, 320]]}]}
```

- `words`：英文词（来自 ASR/映射），毫秒整数；
- `zh_words`：中文词（派生），可为空数组（低置信或 coarse）；
- 旧的 `segments` 字段保留一个版本周期，便于回滚。

## 六、落点与依赖

| 项 | 内容 |
| --- | --- |
| 新模块 | `scripts/zh_align.py`：中文分词、小句切分、DTW、区间切分、置信度；**无网络、可单测** |
| 翻译契约 | `scripts/transcribe.py`（hwmym）与 `scripts/translate_vtt.py`（12 个节目）两条链都要改 prompt + schema + 校验/重试 |
| 模型 | `spacy` + `zh_core_web_sm`（约 12 MB）、`sentence-transformers` + `paraphrase-multilingual-MiniLM-L12-v2`（约 470 MB）；CI 需缓存 |
| 内存/时间 | 每句一次编码；实测 39 句全流程数秒（本机 24 线程） |

## 七、体积与托管

- 240 集（每节目最新 20）：约 **60–90 MB**，Pages 1 GB 上限内可行；
- 全部 4,907 集：约 **1.2 GB**，超出 Pages 上限 → 需要 CDN / 分仓 / 只保留最近 N 集；
- 丢弃 VTT 后站点从 798 MB 降到约 100 MB（feed/index + JSON），这是长期正确的方向。

**但"丢 VTT"不是纯体积决策**：Feed 里的 `podcast:transcript` 目前指向 `.vtt`，消费端（站点播放器 / AntennaPod）
读的也是 VTT。要真正丢弃 VTT，需要同步改：Feed 的 transcript 类型与地址、播放器的解析路径。
本设计第一阶段只**新增 JSON**、保留 VTT；切换消费端单独立项。

## 八、不做

- 不让 LLM 直接吐"词级"对齐（不可机械校验，幻觉率高）。
- 不重建已发布 VTT 的中文（除 align 已有的重写逻辑外）。
- 不在本设计里决定 JSON 的托管位置（Pages/CDN），那是规模问题，先按 240 集做。

## 九、验收

1. 新翻译的句子 **100%** 通过 2.1 的校验（或降级为 coarse 并计数）；
2. 小句级失败率 < 5%；
3. 低置信句占比 < 10%；
4. 抽 1 集人工听感：随机 20 个中文词，词起点偏差 ≤ 0.5 秒；
5. 产物 JSON 能被现有 sidecar 消费方读取（字段向后兼容）。
