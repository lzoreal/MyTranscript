# Windows 全局实时字幕设计（Universal Captions）

日期：2026-11-19
状态：待确认（方向来自用户产品思路文档，本文件为设计稿，未开始实现）
范围：`apps/windows/` 新增原生采集与悬浮窗；`site/` 新增一个独立 overlay 页面；不改 ASR 公共接口语义

## 目标

让 **任何** Windows 应用播放的英文音频都能得到实时、双语、词级的字幕，
并且当这段音频属于我们库里的某一集时，自动换成**官方文字稿**（100% 准确、带词级时间轴）。

一句话定位：**不是"又一个全局字幕"，是"把我们已有的词级双语档案，接到桌面任何声音上"。**

## 与系统功能的差异（必须先想清楚）

Windows 11 自带的 Live Captions 已经能做英文实时字幕，所以"能捕获任意应用"不构成卖点。
我们的差异只有三条：

| 能力 | 系统 Live Captions | 本方案 |
| --- | --- | --- |
| 双语（英→中） | 无 | 有（可开关，默认关） |
| 词级时间戳 | 无 | 有（复用现有词级 JSON） |
| 命中自有节目库时 | 不可能 | 直接换成官方文字稿，识别错误归零 |
| 学习闭环（收藏/复听/导出） | 无 | 后续阶段 |

结论：**采集只是入口，档案匹配才是产品。** 因此 P0 必须先把"采集→字幕"打通，但 P0.5 就要接匹配，
否则做出来的东西打不过系统自带功能。

## 范围（分阶段）

### Phase 1（P0）：设备级捕获 + 悬浮字幕

做：

- WASAPI **设备级 loopback**（默认输出设备的混音），不做进程选择
- 格式探测 + 下混 + 重采样到 16 kHz mono
- 复用 `asr.rs` 现有 sherpa 流式识别，输出部分结果 + 句末结果
- 独立**透明置顶字幕窗**，可拖动、可调透明度、全局热键显隐
- 无音频/静音时明确提示，不产生"幻觉字幕"

不做：进程级选择、节目匹配、翻译、历史落盘。

### Phase 1.5（P0.5）：指纹识别集数 + 载入官方文字稿

> **已否决（2026-11-19）**：用户明确不要指纹认集，这一阶段不进入实现，下面内容仅作设计记录。

- 音频指纹（Chromaprint）索引整库，3–5 秒音频定位「哪一集 + 播放偏移」
- 命中后停用 ASR 结果做显示，改用官方词级 JSON 按偏移滚动
- 偏移持续变化 = 存在插播/剪辑，可作为 DAI 线索

### Phase 2（P1）：进程级捕获 + 热词 + 翻译

- **进程树捕获（已实现）**：`wasapi::Capture::open_process(pid)`，走
  `ActivateAudioInterfaceAsync` + `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`；
  激活参数必须比 client 活得久（`Box::leak`），否则函数返回时堆损坏；
- 入口：命令 `captions_start_process(pid)`、托盘「全局字幕：选择应用…」；
  选择窗 `picker.html` 通过 `IAudioSessionManager2` 枚举正在出声的进程（exe 名 + PID），
  点哪个抓哪个；托盘另保留「只抓前台应用」作为快捷入口；
- 查词：字幕「查词模式」下单词可点，词卡窗 `wordcard.html` 显示音标/释义，
  在线接口 `dictionaryapi.dev` 只接收选中的单词；收藏写入 `vocab.json`；
- 生词本导出：托盘一键写桌面 `MyTranscript-生词本.csv`（UTF-8 BOM）；
- 中文字幕：英文句子稳定后异步翻译（MyMemory，只发该句），第二行显示；
- 术语纠错：`terms.txt` 里 `错写 => 正写`，识别后替换，2 秒内生效；
  热词直接喂解码器在本模型上不可用（词表外 token 会报错）；
- 大小写归一：模型词表是大写子词，输出统一为句首大写、其余小写，术语表里的词保留规范写法；
- 断句：模型不带标点，接 sherpa-onnx 离线英文标点模型（`punct-en`，int8 7.5MB，本地），
  先补标点再按句分行；模型缺失时退回“词间停顿 >0.8 秒补句号”；
  显示默认实时逐字，托盘可切「成句显示」只出整句；
- 双向隔离实测：两个进程同时放不同英文，抓 A 只出 A 的词、抓 B 只出 B 的词，
  另一路 0 次混入；滞后中位 0.25–0.30 s，CPU 5%；
- 热词增强（需切 `modified_beam_search`，见下）
- 字幕中文翻译（仅对稳定句，默认关）

## Phase 1 技术设计

### 数据流

```
默认渲染设备 (IMMDeviceEnumerator, eRender/eConsole)
        │  IAudioClient + AUDCLNT_STREAMFLAGS_LOOPBACK
        ▼
混音格式（通常 48kHz / float32 / 2ch，但不保证）
        │  GetMixFormat → 格式分支
        ▼
下混 mono → 重采样 16kHz f32
        │  采集线程写入环形缓冲（不经过 JS）
        ▼
ASR 工作线程：sherpa OnlineRecognizer::AcceptWaveform
        │  GetResult → partial / final
        ▼
Tauri event "caption" → overlay 窗口
```

关键点：**PCM 不进 WebView**。现在 `asr_feed` 是前端把 PCM 通过 IPC 传给 Rust，
全局字幕模式下这条路径反过来——采集和识别都在 Rust 内闭环，只把文本事件发出去。

### 采集实现要点

1. **设备级优先，不用进程级起手**
   设备级 loopback 自 Vista 起可用，无版本门槛；进程级要求 Build ≥ 20348
   （本机 10.0.26300 满足，但不值得在 P0 引入 `ActivateAudioInterfaceAsync` 的复杂度）。

2. **格式不能假设**
   `GetMixFormat()` 可能返回 `WAVEFORMATEXTENSIBLE`：
   - 32-bit float / 16-bit PCM
   - 44.1k / 48k（蓝牙设备切换时还会变）
   - 1–2 声道
   必须按 `wFormatTag` + `SubFormat` 分支处理；不认识的格式直接报"不支持的音频格式"，
   不要静默按 float 解析。

3. **重采样质量会影响 WER**
   48k→16k 用线性插值会有混叠，实测通常带来 2–4% 的相对 WER 上升。
   Phase 1 允许先用带简单低通的线性重采样跑通，但要在验收里记录 WER 变化；
   若不达标再换多相滤波。

4. **设备切换要能自愈**
   耳机插拔、默认设备变更、格式变更都会让旧流失效。
   Phase 1 用 2 秒轮询默认设备 + 格式指纹（比实现 `IMMNotificationClient` 便宜），
   不一致就重建流，重建期间字幕窗显示"正在切换音频设备"。

5. **静音判定**
   连续 2 秒 RMS < -50 dBFS：
   - 不往 ASR 送数据（省 CPU）
   - 浮窗显示"未捕获到音频（系统静音或该应用使用独占模式）"
   这条很重要：独占模式 / DRM 内容 loopback 会拿到静音，不能装作在识别。

### ASR 侧改动

- 新增 `captions_start(device?)` / `captions_stop()` / `captions_status()` 三个命令
- 识别参数与播放器模式分离：字幕模式要**开端点检测**（`enable_endpoint = 1`，
  `rule1_min_trailing_silence ≈ 0.8s`），否则句子永远不 final；
  播放器模式现在是 `enable_endpoint = 0` + 2.4s，两者不能共用一套常量
- 部分结果节流：最多 5 次/秒 emit，避免 IPC 和 DOM 抖
- 线程数：字幕模式默认 **1 线程**（实测 2 线程只会把 CPU 抬到 10 倍，滞后不变）

### 悬浮窗

Tauri 2 在 Rust 侧建窗，不写进 `tauri.conf.json`（要按运行时设置改属性）：

- `transparent(true)` / `decorations(false)` / `always_on_top(true)` /
  `skip_taskbar(true)` / `focus(false)` / `shadow(false)`
- 点击穿透默认**开**（`set_ignore_cursor_events(true)`），否则会挡住鼠标；
  按热键切到"可交互"再拖动/调透明度
- 位置与透明度存 `prefs`，按显示器物理像素保存，换 DPI 时按比例换算
- 页面：新增 `site/overlay.html`（独立小页面，只订阅 `caption` 事件 + 渲染 2–3 行）
- 全屏独占游戏（exclusive fullscreen）不保证可见，设计上接受，不做 hook

### 全局热键

现有 `main.rs` 已用 `RegisterHotKey` + `GetMessageW` 线程注册了 3 个键位（含 0xB3 播放暂停）。
字幕模式复用同一线程，新增两个键位：

- 显隐字幕窗
- 切换点击穿透

注意 `RegisterHotKey` 冲突会让注册失败，要在 UI 上暴露"热键被占用"，不要静默降级。

### 依赖

`windows-sys` 目前只有 Foundation / KeyboardAndMouse / WindowsAndMessaging。
需要补 `Win32_Media_Audio`、`Win32_System_Com`、`Win32_System_Threading`。

建议：**采集模块用 `windows` crate（带 COM 包装）**，热键继续留 `windows-sys`。
裸 `windows-sys` 写 COM 的 `QueryInterface`/`Release` 极易漏引用计数，这类 bug 在音频线程里表现为随机崩溃，
不值得为省一个依赖去手写。

## Phase 1.5 技术设计（差异化核心）

### 为什么不用 ASR 文本匹配

用户文档里提出"识别几秒英文 → 在文字稿里找匹配 → 定位集数"。
问题：

- 20M 模型对通用音频 WER 约 10–15%，专有名词更差，文本匹配的召回不稳
- 要在整库文字稿里做模糊检索，成本高且容易误配
- 匹配成功也只能给出"哪一集"，给不出**精确偏移**

### 用音频指纹

- 每集离线算 Chromaprint 指纹（45 分钟约 1KB），整库索引很小
- 实时端持续算最近 10 秒指纹，在索引里查子序列匹配
- 命中输出：`episodeId` + `offsetSeconds` + `confidence`
- 偏移随时间的变化曲线：
  - 恒定 → 正常播放
  - 阶跃 → 插入了不在原音频里的内容（DAI / 剪辑）
  - 漂移 → 变速播放（0.8x 等），可反推播放速率

这条管线同时解决三件事：自动认集、精确对齐、DAI 线索。
**它是本方案唯一真正的护城河，优先级应高于进程级捕获。**

### PoC 实测（2026-11-19，已否决，仅存档）

先不引入 Chromaprint，用纯 numpy 的「频谱峰值 + (f1,f2,Δt) 哈希对」验证可行性：
`scripts/fingerprint_poc.py`，测试在 `tests/test_fingerprint.py`。

素材：SmartLess 两集真实音频（只取前 12.5 分钟 / 8.3 分钟，8 kHz mono）。

| 项 | 结果 |
| --- | --- |
| 索引（约 21 分钟素材） | 13.7 万唯一哈希 / 97.4 万 postings（约 780 postings/s） |
| 10 s 查询 @60/180/300/420 s | 集数全对，偏移误差 < 0.1 s；得分 5.5k–9.2k，次优 ≤65 |
| 加噪（σ=0.01）/ 音量 0.25× / 削波 3× | 仍全对，得分 4.5k–8.3k |
| 64 kbps mp3 重编码后再查 @200 s | 200.0 s，得分 5032（次优 58） |
| 5 s @123.4 s | 123.39 s（743 vs 41） |
| 3 s @301.7 s | 301.70 s（624 vs 20） |
| 负样本（ep2 片段查只有 ep1 的索引） | 63 分，与正样本差两个数量级 |
| 查询耗时 | 18–49 ms（Python + numpy，含哈希与投票） |

结论：**这条路线在本库素材上成立**，3 秒就能定位，偏移精度高于字幕滚动所需的粒度。

尚未解决的工程问题：**索引体积**。780 postings/s 意味着 45 分钟一集约 210 万条，
按 `(hash, episode, frame)` 12 字节算约 25 MB，和「Chromaprint 45 分钟 1 KB」不是一个量级。
要上整库（14 集 × 数十集）必须先压缩：频率量化到 6 bit、每哈希限 3–4 条 posting、
只索引节目正片（去掉广告段），目标把整库压到 10 MB 以内并在内存里 mmap。

### 命中后的显示

- 用 `offsetSeconds` 在官方词级 JSON 里定位当前词，按词级时间轴滚动
- 官方稿有中文，直接双语显示，无需翻译
- 偏移跳变时插入一条"此处有 XX 秒非原文内容"的提示条，而不是把字幕错位

## 与 cue 级跳过（2026-11-19）的关系

两者共享同一个前提：**文字稿时间轴与真实音频对得上**。

- 现在的 cue 级跳过只在"离线音频 + 本机自转写"生效，就是因为外部音频可能被 DAI 改过时间轴
- 指纹偏移能给出真实偏移，跳过逻辑可以从"只敢在自转写集生效"扩展到全库
- 顺序建议：先做指纹偏移，再回头放宽跳过的门控

## 验收标准（Phase 1）

必须可测，不能"看起来能用"：

1. 打开任意应用播放英文音频，**首行字幕 ≤ 1.5s** 出现，稳态滞后 **≤ 1.0s**
2. CPU：单核占用 ≤ 30%，整机 ≤ 8%（8 核基准）；连续 30 分钟无内存增长
3. 系统静音 / 独占模式：3 秒内出现"未捕获到音频"提示，**不产生任何字幕**
4. 耳机↔扬声器切换：10 秒内自动恢复出字，不崩溃、不残留旧流
5. 关闭字幕：线程、COM 对象、音频句柄全部释放（任务管理器无残留）
6. 全程不联网（抓包确认）；翻译开关关闭时无任何文本外发
7. 浮窗：置顶、点击穿透、热键显隐、多显示器拖动位置正确
8. 新开一路字幕时的首句丢失必须显式处理：要么 ≤ 0.3 秒，要么在 UI 上明说（不允许静默吞掉）

## 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 重采样劣化 WER | 字幕错词变多 | 先在真机上量，再决定是否上多相滤波 |
| 20M 模型延迟超预期 | 首行 > 2s，体验崩 | 降 chunk、开 2 线程；必要时换成更小的流式模型 |

| 全屏独占游戏不可见 | 场景受限 | 明确不支持，不做注入 |

## Spike 实测（2026-11-19）

工具：`apps/windows/capture-spike`（设备级 loopback，复用 `asr.rs`，PCM 不进 WebView）。

环境：Windows 10.0.26300 / 26H2；设备混音 48000 Hz / 2ch / float32；模型 en-mini。

方法：系统 TTS 念英文段落（干净语音），采集 28–30 秒，统计「送入音频位置 − 最后一个词时间戳」。

| 指标 | 1 线程 | 2 线程 |
| --- | --- | --- |
| 识别滞后 中位 | **0.25 s** | 0.27 s |
| 识别滞后 p95 | 0.44 s | 0.44 s |
| 进程 CPU（单核%） | **3%** | 31% |
| 静音时行为 | 不产包、不出字 | 同 |

两个结论直接改变设计：

1. **识别线程数定 1。** 2 线程没有降低滞后，CPU 反而高一个数量级（ONNX Runtime intra-op 自旋）。
2. **流式模型每次启动会吞掉开头约 1.4 秒。**
   `timestamps` 稳定从 1.48–1.80 s 开始，前面的词完全不出现；模型元数据
   `decode_chunk_len=32` / `left_context_len=64` 与这个量级吻合。
   前置静音（1.5 s、2.0 s）实测**无效**，反而丢得更多，说明不是简单补零能解决的。

第 2 条的后果：每次新开一路字幕，第一句话会缺一截；持续收听不受影响。
这不是采集问题——把采集音频 dump 出来离线识别，丢失位置完全一致。

待定方案（按成本排序）：

- **接受**：字幕窗在启动时显示「正在听…」1.5 秒再出字，把丢失说清楚；
- **窗口补救**：前 2 秒用离线模型（paraformer/whisper-tiny）补一遍，再切流式；
- **换引擎**：选 left context 更小的流式模型，或全程用 2–3 秒窗口的离线识别（滞后会升到 1 s 左右）。

**已定（2026-11-19）：接受 + UI 明说。** 具体行为：

- 启动一路字幕时，浮窗先显示「正在听…」（低对比度、不占主行），约 1.4–1.5 秒后第一行文字出现；
- 2 秒内没有捕获到音频，改显示「未捕获到音频（系统静音，或该应用使用独占模式）」；
- 任何情况下都不放占位词、不猜测内容——宁可空着，也不能让用户以为那 1.4 秒被识别了。

这个结论也适用于现有播放器的实时识别——同一套 `asr.rs`，同样的开头丢失。

## P0 落地（2026-11-19，桌面壳已实测）

采集 spike 的 `wasapi.rs` 已迁进 `src-tauri/src/wasapi.rs`（spike 用 `#[path]` 复用同一份），
桌面壳新增 `src-tauri/src/captions.rs` 与 `site/overlay.html`：

- 托盘菜单「全局字幕（实验）」、全局热键 **Ctrl+Alt+L** 都可开关；关掉会销毁字幕窗、停掉采集与识别；
- 字幕窗：900×132、无边框、透明、置顶、不进任务栏、默认鼠标穿透，底部居中、离任务栏 90 px；
- 事件 `myt://caption`，payload `{text, listening, silent, active, error}`；超长文本只保留尾部 600 字符；
- 托盘另有「字幕窗可拖动」「字幕透明度」：拖动模式会关掉鼠标穿透并显示虚线框，
  透明度按 88% → 72% → 55% → 100% 循环；命令 `captions_set_drag` / `captions_set_opacity` 也可直接调；
- 音频设备每 2 秒巡检一次默认渲染设备，耳机↔扬声器切走后自动重建采集（`pump` 报错时也会先重连一次）；
- 联调：`MYT_CAPTIONS_AUTO=1` 开局自动开字幕，`MYT_DEBUG=1` 把每行文本写进 `%TEMP%\myt-mini.log`。

实测（Windows 10.0 build 26300 / 26H2，系统 TTS 念英文）：

| 场景 | 结果 |
| --- | --- |
| 完全无音频 | 不产包、不出字；2 s 后显示「未捕获到音频…」 |
| 英文 TTS 连续播放 | 实时出字，两行内完整显示，无横向截断 |
| Ctrl+Alt+L 关闭 | 字幕窗关闭，进程与主窗正常，再按可重开 |
| 开头丢失 | 稳定存在，首行从语音约 1.4 s 之后开始 |

两个实现层面的坑（都已处理）：

1. **高 DPI**：`inner_size` 设的逻辑尺寸会被 WebView 按 1.5 倍渲染、再按物理尺寸裁切，
   导致右侧三分之一看不到。建窗后补一次物理尺寸锁定，并按 `outer_size()` 居中。
2. **换行**：这台机器的 CSS 视口宽度和窗口物理宽度不成比例，`measureText` 量出来的宽度偏大，
   按像素换行仍会溢出。字幕改为**按字符数硬断行**（每行 ≤44 字符），两行封顶。

明确不做（P0 范围外）：麦克风输入、进程级捕获、中文翻译、字幕窗拖动/调透明度（当前全穿透）。

## 未决问题

- 字幕窗是"单行滚动"还是"三行上下文"？影响信息密度与遮挡面积。
- 中文翻译走现有翻译服务还是本地模型？离线优先原则下，云端翻译是明显的例外，需要单独确认。
- 指纹索引放本地 SQLite 还是内存文件？整库很小，倾向于内存 mmap。
- 是否需要"仅在我们库内的节目才出字幕"的省电模式？对纯学习场景可能更实用。
